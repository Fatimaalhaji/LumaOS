# LumaOS Core

LumaOS is a personal AI operating layer. Phase 2 adds the Memory Engine foundation for persistent personal context while keeping AI providers, agents, document ingestion, vector databases, pgvector, and semantic embeddings intentionally deferred.

## Current architecture

- **Next.js App Router** renders protected application screens and server actions.
- **Auth.js** provides credential-based local authentication and server-side sessions.
- **PostgreSQL + Drizzle ORM** store users, profiles, goals, tasks, memories, conversations, and messages.
- **Zod** validates environment variables and all user input accepted by server actions and memory services.
- **Vitest** covers validation and basic ownership logic.

## Memory Engine architecture

Memory access follows this boundary:

```text
UI
  ↓
Server Action
  ↓
Memory Service
  ↓
Repository / Database
```

The UI must not query memory tables directly. `server/services/memory.ts` is the server-side boundary for creating, reading, listing, updating, deleting, searching, and retrieving relevant memories. The service accepts the authenticated user id derived by server code and never trusts a client-supplied `userId`.

### Memory types

LumaOS intentionally keeps a small memory taxonomy:

- `PROFILE`: Stable information about the user's profile/context.
- `PREFERENCE`: How the user prefers things to be done.
- `GOAL`: A persistent objective the user is working toward.
- `FACT`: A factual piece of information explicitly provided by the user.
- `KNOWLEDGE`: Information the user wants LumaOS to retain.
- `PROJECT`: Information associated with an ongoing project.

### Memory sources

Memory sources are controlled values:

- `USER`: Information explicitly saved by the user.
- `SYSTEM`: Information generated by trusted LumaOS system processes.
- `ASSISTANT`: Information that may eventually be extracted by the AI assistant.

The current application only creates `USER` memories from the Memory UI. It does not automatically create `ASSISTANT` memories.

### Memory ownership model

A user can only read, create, update, and delete their own memories. Server actions derive the authenticated user id from the Auth.js server session. Every memory read/update/delete is scoped by both `memories.id` and `memories.userId`, so another user's memory behaves as not found and does not leak existence.

### Search and relevance

Phase 2 implements PostgreSQL-compatible lexical search with Drizzle query builders. Search is user-scoped, uses safe parameterized conditions, searches memory content with `ILIKE`, optionally filters by memory type, and applies a bounded limit.

`getRelevantMemories()` is a temporary lexical relevance implementation. It combines exact/partial keyword matches, importance, and recency, and always returns a small bounded result set. Semantic embeddings are intentionally deferred. Future phases can replace or augment lexical relevance with embeddings, pgvector, and vector search without changing UI components.

## Context Engine

Context access follows this boundary:

```text
UI / future AI
  ↓
Context Service
  ↓
Memory + Goals + Tasks + Profile
```

`server/services/context.ts` builds structured user context only. It does not generate AI responses. The current shape is:

```ts
{
  profile,
  activeGoals,
  openTasks,
  memories,
  limits,
}
```

Context loading is intentionally bounded: one profile record, five active goals, ten open tasks, and eight relevant memories. LumaOS must never load a user's entire database into future AI context.

Unfinished future systems: AI model calls, autonomous agents, plugin marketplace, document ingestion, vector embeddings, external integrations, and advanced permissions.

## Tech stack

Next.js, React, TypeScript strict mode, pnpm, Tailwind CSS, Drizzle ORM, PostgreSQL, Auth.js, Zod, and Vitest.

## Local development

```bash
pnpm install
cp .env.example .env
pnpm dev
```

## Environment variables

- `DATABASE_URL`: PostgreSQL connection string.
- `AUTH_SECRET`: strong random secret for Auth.js.
- `AUTH_TRUST_HOST`: set to `true` for local/proxy deployments as needed.
- `AI_PROVIDER`, `AI_API_KEY`: placeholders for later phases. No AI provider is implemented yet.

Never commit real secrets.

## Database setup

Start PostgreSQL locally, set `DATABASE_URL`, then run:

```bash
pnpm drizzle-kit generate
pnpm drizzle-kit migrate
```

The initial schema includes `users`, `profiles`, `goals`, `tasks`, `memories`, `conversations`, and `messages`. Memory rows include metadata fields reserved for a later pgvector migration.

## Authentication setup

LumaOS uses Auth.js credentials authentication for local development. Registration stores a bcrypt password hash and login creates a JWT-backed session. Social providers are intentionally not configured yet.
